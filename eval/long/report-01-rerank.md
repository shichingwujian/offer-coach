## 四、失分点逐条诊断

### 🔴 高危 A：reranker 的定位被引导性追问带偏（**最严重**）

> 面试官：那这个 reranker 相当于给向量通道加权吗？
> 候选人：**对，差不多就是加权，就是把向量那边的权重调高一点。**

**这是错的。** 而且错得可惜——候选人前一段刚说过"粗排海选进前 30，裁判复评后再发奖""再强的复评也救不了没进前 30 的题"，这**恰恰是 reranker 的正确理解**。结果一句"差不多就是加权"，把前面的正确表述全部推翻了。

**题库标准答案对照：**

> 粗排用双塔等可预计算表示快速召回，目标是保住召回率；Cross-Encoder 把 query 和候选文档**拼接后共同输入模型**，通过**跨文本注意力**直接判断匹配度，能识别词序、否定、条件等细粒度语义。它不是对某一路通道加权，而是一个**独立的、与召回通道正交的判决层**——它既不知道也不关心这道题是从 FTS5 来的还是从向量通道来的，RRF 之后所有候选对它一视同仁。

**为什么这个错误致命：**

1. 面试官问的是**诱导性问题**（"相当于……吗？"）。顺着答就等于承认自己没真正理解自己搭的架构。
2. "给向量通道加权"这个描述，在技术上还隐含了另一个错误——RRF 之后已经没有"通道"概念了，名次信息是融合后的。
3. 一旦承认是加权，面试官就会想：**那你前面说的"语义相近的排前面"是不是也是猜的？**

**正确话术（可直接背）：**

> "不是的，这两个不是一回事。RRF 是**融合层**，只在名次上做算术，对两路一视同仁；reranker 是**判决层**，它把 query 和候选原文拼成一对送进 cross-encoder 逐对打分，靠的是跨文本注意力，能识别否定、条件、词序这些双塔抓不到的东西。它不区分候选来自哪一路——到这一级，通道身份已经不重要了。硬要类比的话，加权是给两个考官的分打折扣，reranker 是另请一个考官把卷子重读一遍。"

### 🔴 高危 B：余弦相似度"受向量长度影响"（基础硬伤）

> 候选人："我记得余弦在向量特别长的时候也会受长度影响，因为它俩本质上差不多。"

**错误。** 余弦相似度的定义就是除以模长，**在任何维度下都完全不受向量长度影响**。候选人把两件事搞混了：

| 现象 | 真实原因 |
|---|---|
| 高维向量下余弦"退化" | **维度灾难**导致的距离集中（concentration of distances），所有点对余弦都趋近某个常数，区分度下降——不是"受长度影响" |
| 长文本效果差 | 长文本被 embedding 压成一个向量后**语义被平均掉**，信息损失，与"长度影响余弦"无关 |
| 点积受长度影响 | 这是对的 ✅ 点积 = 余弦 × 两个模长的乘积 |

**题库对照（已召回）：**

> 余弦只看方向、不看长度，值域 [-1,1]；用余弦而非欧氏距离，正是因为 embedding 对不同长度文本的模长差异大，欧氏距离会把"语义相同但长短不同"判远。余弦归一化了长度，语义相同的文本无论长短都趋近 1。工程上还有三个用途：检索 top-K、去重（>0.95 判近重复）、阈值过滤（<0.6 直接丢，不进精排）。

**正确话术：**

> "余弦对长度完全不敏感，因为它除以了两个模长，只看夹角。会受长度影响的是点积——点积等于余弦乘两个模长。如果 embedding 已经归一化了，两者排序完全等价，很多向量库内部直接算点积省一次开方。真正会让余弦变得不好用的是另一件事：高维下的距离集中，所有 pair 的余弦都挤在一起，区分度下降。至于长文本效果差，那是长文本被压成一个向量后语义被平均掉了，跟余弦没关系。"

**补充加分（如果面试官继续问）：**"Milvus/Qdrant 这类库 ANN 阶段用的是 HNSW/IVF 近似搜索，不是暴力遍历，精确余弦只在小候选集上算。"

### 🟡 中危 C：bge-small vs bge-m3 的选型理由太薄

> 候选人："主要是 bge-small 比较小，下载快。大模型效果应该会好一点，但我觉得检索不准更多是别的问题，就先没换。"

"下载快"是**个人开发视角**，不是工程视角。而且后半句"检索不准更多是别的问题"——方向对，但你**没有给出证据**，听起来像找借口。

**补救框架（四个维度 + 一个数据）：**

> "当时是按四个维度选的：**维度**（bge-small 是 512 维，bge-m3 是 1024 维，索引体积和内存差一倍）、**延迟**（small 在 CPU 上单条 query 编码约十几毫秒，m3 要慢数倍，我这个是本地跑、不花 API 钱，就得吃这个延迟）、**语言**（我这是纯中文题库，m3 的多语言优势用不上）、**MTEB 中文检索分**（m3 确实更高，但差距在纯中文短 query 场景没有量级差）。
>
> 更关键的是我做过归因：92.6% 之后剩的 4 条全是**召回病**——目标题连粗排前 30 都没进。换更大的 embedding 是能改善这一层，但我当时判断瓶颈顺序上，同义词扩展和题库补内容的边际收益比换模型高。如果重来，我会**用一个对照实验说话**：固定评估集，换 m3 跑一遍 recall@5，看涨几个点，再决定值不值那一倍延迟。"

### 🟡 中危 D：token 估算方式过于粗糙

> "token 数是中文字符按一个 token 估算的。"

中文在 BGE/GPT 系 tokenizer 下通常约 **1 字 ≈ 1.0–1.7 token**（BPE 中文词表覆盖好时接近 1，覆盖差时更高）。按 1:1 估算会**系统性低估**，滑窗触发会比预期晚——在逼近上限时才触发，恰恰是最危险的位置。

**修复话术：**"我用的是保守估算，1 中文字 ≈ 1 token，英文 4 字符 ≈ 1 token。但这是个**下界**，实际会偏高，所以我给滑窗留了 20% 的 buffer。更严谨的做法是直接用 tiktoken 或 tokenizer 精确计数——成本很低，纯本地计算，我当时是嫌依赖多。这个如果上生产我会换成精确计数。"

### 🟢 低危 E：摘要压缩"没做"——回答合格，但可以更主动

目前的回答（"一次就四五轮，离上限远，摘要是又花钱又可能出错"）**逻辑自洽，是可接受的主动裁剪**。但可以再加一层，显示你知道正确做法：

> "如果真要做，我会做**增量摘要而不是全量重算**——已有的摘要 S 加上新一轮对话，只对这两部分重新总结，不重放原始历史。全量重算是 O(n²) 的 token 消耗。而且摘要有**信息腐蚀**风险，越压越失真，所以我更倾向滑窗 + 关键信息钉住（把结论、待办这类结构化字段单独拎出来，不参与滑动），而不是纯摘要。"

### 🟢 低危 F：弱点"只坐实不洗白"——承认得漂亮，但差一句设计

候选人的坦白（"洗白规则麻烦，先简化掉了，这确实是 TODO"）是**加分**的。但要防止面试官想"那你就是没想"。

**补一句：**"如果补，我的思路是**衰减 + 反证**双机制：一是时间衰减，超过 N 次诊断未复现，坐实度按系数递减；二是反证，某维度这次打分 ≥ 4 且连续两次，就把对应弱点坐实度打对折，而不是直接清零——因为一次表现好可能是题简单，直接清零会让画像变得过于乐观、失去参考价值。核心是**降权而不删除**，保留历史轨迹。"

## 六、必须修正的两个认知（记忆卡）

```
❌ 余弦相似度会受向量长度影响
✅ 余弦 = 只看夹角，永远不受长度影响。
   受长度影响的是点积（= 余弦 × 两个模长）。

❌ reranker 是给向量通道加权
✅ reranker 是独立的判决层，与召回通道正交。
   RRF = 融合层（只在名次上做算术）
   Reranker = 判决层（query×doc 拼接过 cross-attention）
   到这一级，通道身份已经不存在了。
```
