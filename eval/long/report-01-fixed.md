1. **手写 Harness 的动机陈述正确**。"不想只会调框架"——这是唯一站得住脚的不用框架理由，比"框架太重"高级。且能立刻用 while 循环 + 工具下单 + 收尾条件证明不是空话。

## 四、薄弱点（按优先级）

### 【P0】cross-encoder reranker 的定位错误——被面试官一句话带偏

**现场原话**
> 面试官："那这个 reranker 相当于给向量通道加权吗？"
> 候选人："对，差不多就是加权，就是把向量那边的权重调高一点。"

**问题在哪**
1. 位置错了。加权发生在**融合前**（对某一路的分数乘系数，或调 RRF 的 k），cross-encoder 发生在**融合后**（对每个候选重新打分）。
2. 机制错了。cross-encoder 是 query 和 doc **拼在一起过跨注意力**，直接判断匹配度，能吃到词序、否定、条件——它拿到的是**一手信息**。这恰恰是你上一句"RRF 用的是名次，是二手信息"的对照物，而"加权"这个答案把自己刚建立的优势抹掉了。
3. 这是**面试官设的陷阱**（用一个错误类比试探），顺着答等于承认"我加这层精排只是调了个权重"，那么 RRF 的设计价值、精排的必要性同时被削掉。

**题库标准口径**（《粗排后为什么需要使用 Cross-Encoder 重排？两阶段检索如何分工？》）
> 粗排用可预计算表示（双塔）快速召回，目标是保住召回率；Cross-Encoder 把查询和候选文档拼接后共同输入，通过跨文本注意力直接判断匹配度，能识别词序、否定、条件和细粒度语义，因此往往比单纯向量相似度更有判别力。**它需要对每个候选逐一推理，候选过多会带来延迟和成本**——所以候选规模必须固定（你的 top-30 就是这个约束）。

**建议话术（可直接背）**
> "不是加权。加权是融合层的事——如果我要调通道权重，那是在 RRF 之前对两路分数做归一化再乘系数，或者调 k 值。cross-encoder 在融合之后，它拿到的是 query 和题目的原文，逐对过跨注意力，是**用一手信息重新判分**，而不是给某个通道调系数。代价是每个候选都要前向一次，所以候选必须锁在 30 条以内。"

### 【P1】余弦相似度 / 点积：前半句对，后半句是自我污染

**现场原话**
> "……不过我记得余弦在向量特别长的时候也会受长度影响，因为它俩本质上差不多。"

**问题在哪**

这句话把一个**真现象**和**假结论**粘在了一起：
- 真的部分：余弦对**长度（模）**完全不敏感，因为分母 |A||B| 已经归一化。点积才是 |A||B|cosθ，只有向量**未归一化**时才受长度影响。
- 他大概想起了"高维空间里随机向量趋于近似正交、余弦值集中、区分度下降"（维度灾难），但把它错译成了"长向量受长度影响"。
- 更要命的是"本质上差不多"——直接否定了自己在用余弦做检索这件事的合理性。

**题库标准口径**（《什么是余弦相似度？在 RAG 系统中用来做什么？》）
> 余弦衡量两个向量方向的接近程度，不关心长度，只关心角度；值域 [-1,1]。Embedding 输出的向量模长差异很大，用欧氏距离会让语义相同的长短文本距离很远，余弦归一化了长度，语义相同的文本无论长短余弦都接近 1。工程补充：若向量已做 L2 归一化，**内积 = 余弦**，可以用点积换取速度。另外向量库（Milvus/Qdrant）的 ANN 检索用 HNSW/IVF 近似算法，精确余弦只在小候选集上做。

**建议话术**
> "余弦只看方向，模长在分母里被约掉了，所以长度无关；点积 = |A||B|cosθ，未归一化时会被长向量放大。工程上 bge 输出我做了 L2 归一化，这时内积就等于余弦，用点积能省一次归一化的开销。真正会让余弦变钝的不是长度，是高维下随机向量趋于集中、区分度下降——这也正是我后面要加 cross-encoder 的动机之一。"

（最后一句能把失分点转成加分点，把两个薄弱环节缝起来。）

### 【P1】Embedding 选型：有尺子却没量

**现场原话**
> "主要是 bge-small 比较小，下载快。大模型效果应该会好一点，但我觉得检索不准更多是别的问题，就先没换。"

**问题在哪**
- "下载快"是开发期体验，不是选型维度，在面试官耳朵里等于"我没想过"。
- 事实层面你也吃了亏：题库只有 807 条，**离线预计算是一次性的**，换 bge-m3 的增量成本只有索引体积和单条 query 的编码延迟，远没到需要犹豫的量级。你用"成本"当理由，但这个场景的成本其实几乎为零。
- 最可惜的是：**你自己有 54 条评估集和 recall@5 这把尺子**，换模型 A/B 一次的成本是几分钟。"我有尺子但没量"比"我不知道怎么量"更扣分。
- 顺带：后半句"检索不准更多是别的问题"**方向是对的**（你自己已经把漏网的 4 条定位成召回病），但你只说了"我觉得"，没给证据。

**题库标准口径**（《Embedding 模型怎么选？选型时考虑哪些因素？》）
> 六维：语言支持 / 向量维度 / 检索精度（MTEB、C-MTEB）/ 推理速度 / 部署成本 / 最大长度。关键认知：**公开 benchmark 排名不等于你的场景效果，必须在自己的数据上做 A/B，构建几百条 (query, relevant_doc) 跑 Recall@K 和 MRR，用数据说话。**

**建议话术**
> "按六维看：中文场景 BGE 系列本来就合适；维度上 small 是 512 维、m3 是 1024，存储和检索成本翻倍；精度上 m3 在 C-MTEB 更强，但我的场景是短问题对短题目，长文本优势用不上。更关键的是我手上有 54 条评估集，换模型跑一次 recall@5 就知道——我没跑，是因为现有 92.6% 的漏网 4 条已经定位在粗排召回而不是编码质量，换编码器大概率不解决这 4 条。但正确的做法是先量再说，这一点我事后复盘是欠的。"

### 【P2】记忆只坐实不洗白：诚实但欠一个方案

**现场原话**
> "现在不洗，只坐实不洗白……这个确实是 TODO。"

坦白加分，理由（规则难定）也成立。但收尾太软——面试官问的是"怎么设计"，你答的是"我没设计"。

**题库对照**（《每轮对话都触发长期记忆存储，用户记忆快速积累、存得过多怎么办？》）
> 核心不是"存太多"，而是缺少准入与质量管理；分四层：写入准入 → 去重合并 → 冲突处理（保留最新、旧值降权）→ 衰减与归档。只增不减会让画像永久失真，可能把三个月前的旧结论一直顶在前面。

**建议话术（三层，全部是死规则，不违背你"不让模型判断"的原则）**
> "1）时间衰减：坐实度按半衰期打折，长期没复现的弱点自然降权；2）反证抵消：同一维度这次 ≥4 分，且命中的是历史弱点对应知识点，坐实度 -0.5；3）连续 N 次达标就归档成'已改善'而不是删除——保留轨迹，因为进步曲线本身就是这个产品的卖点。负向写入和正向写入一样都是规则，不引入模型判断。"

**一句能加分的话**："弱点只增不减是产品问题不只是工程 TODO——老用户第二次来，看到的还是三个月前的自己。"

### 【P3】上下文管理：细节到位，缺"预留输出预算"

- **对的地方**：滑窗 + 成对丢弃工具调用与回执（孤儿 tool_call 会 400）——这个细节有真实踩坑痕迹，值得讲；死保区（system + 首条用户消息）也是对的。
- **可改进**：token 按"1 中文字符 = 1 token"估，方向偏保守但会系统性高估（多数 BPE 中文约 0.6–0.7 token/字），预算会被过早触发、白扔历史。另缺一句**为输出和工具结果预留预算**——题库口径是"接近上限时预留输出与工具调用预算，按优先级裁剪，同时把完整历史落外部存储"。
- **防守得好**：追问"早期信息丢了怎么办"时，你用"4-5 轮远未到上限 + 摘要又贵又易错"回答——**用真实用量数据否决一个时髦方案**，这是全场最漂亮的防守之一，保持这个习惯。
