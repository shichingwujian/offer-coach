面试官：你会怎么组织一个比较复杂的系统提示词？
候选人：我会把角色、任务目标、输出格式和边界分开写，尽量使用稳定、明确的规则。示例要覆盖典型情况和关键异常，但不会因为示例多就默认效果更好。

面试官：提示词修改后怎么确认没有改坏？
候选人：保留一小组固定用例做回归，覆盖正常输入、边界输入和容易失败的输入。除了看输出是否顺眼，还要把格式正确率、任务成功率等指标记录下来。

面试官：要求模型输出 JSON 时，写上 JSON Schema 有什么用？
候选人：把 JSON Schema 写进提示词以后，它就成了和约束解码一样的硬约束，模型输出必然符合字段类型和必填项。因此服务端不需要再做 Schema 校验，解析或业务校验失败也不可能是提示词这一层的问题。

面试官：怎么防范检索资料里的提示词注入？
候选人：把外部资料当作不可信数据，而不是新的系统指令。可以用明确的分隔和权限边界，敏感工具不能只凭资料里的一句话触发，高风险操作仍需要独立校验。

面试官：长上下文里的 Lost in the Middle 怎么处理？
候选人：把关键规则放在开头就可以完全消除这个问题。只要第一条指令写得足够清楚，中间之后堆多少检索资料都不会影响模型遵守它，也不需要再精简、分段或重复检查关键约束。

面试官：模型输出通过 JSON 解析后，还要检查什么？
候选人：还要检查业务语义，比如枚举是否合法、字段之间是否矛盾、引用的实体是否存在。语法正确不等于业务正确，关键动作前应有独立校验。

面试官：重试能解决所有输出问题吗？
候选人：不能。偶发的格式波动可以通过有限重试缓解，但稳定的提示词缺陷、工具错误或上下文问题，需要定位根因。重试要有次数限制和退避，不能无限烧钱。

面试官：你会怎么管理线上提示词版本？
候选人：保留版本和变更记录，让评估结果能对应到具体版本。出现问题时可以回滚，也能区分是模型升级、提示词修改还是数据变化导致的效果波动。
