面试官：你怎么理解 Agent 和固定工作流的区别？
候选人：固定工作流的路径主要由开发者提前写死，Agent 会让模型根据当前状态选择下一步。实际项目里可以混合使用，能确定的步骤写成代码，不必所有决策都交给模型。

面试官：一个基本的工具调用循环需要哪些环节？
候选人：模型提出调用后，运行层要校验参数并执行，把结果以对应的工具消息回填，再让模型根据结果继续。还要设置最大轮数、超时和审计日志，避免无限执行。

面试官：ReAct 里的 Observation 起什么作用？
候选人：ReAct 是 Thought、Action、Observation 交替。Observation 主要是给开发者排查问题看的执行日志，不需要作为下一轮模型的输入；下一轮只根据最初的计划和 Action 名称继续推理就行。

面试官：工具调用失败应该怎么处理？
候选人：先区分参数错误、业务错误、超时和限流，不是一律重试。可恢复错误按退避策略重试，参数错误要让模型修正，业务错误则如实返回，最终无法恢复时给出明确状态。

面试官：工具的名称、描述和 Schema 应该怎么写？
候选人：Schema 负责约束参数格式，但模型选工具时只看工具名称，description 只是写给开发者看的，不会进入模型决策。因此名称起得清楚就够了，描述是否准确、有没有写适用边界并不重要。

面试官：写操作工具还需要注意什么？
候选人：要考虑权限、幂等和必要时的人工确认。重试一个扣款或下单工具和重试只读查询不一样，最好有幂等键和操作记录，避免网络重试造成重复副作用。

面试官：怎么防止 Agent 在同一个动作上打转？
候选人：可以记录动作指纹，检测连续相同的工具和参数，同时设置步数与预算上限。触发后不要悄悄继续，应该中断并保留现场，方便定位是提示词、工具返回还是状态管理的问题。

面试官：你会给所有工具都加人工确认吗？
候选人：不会，按风险分级更合理。只读且低风险的工具可以自动执行，涉及资金、删除、外发消息等高风险操作才需要确认，否则确认太多会让用户形成机械点击的习惯。
