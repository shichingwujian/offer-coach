## 架构图

```text
        ┌──────────────────────────────────────────────┐
        │                AgentLoop.run                  │
        │                                              │
        │   history = [system, user_goal]              │
        │        │                                     │
        │        ▼                                     │
        │   校验历史协议（id 因果链完整？）              │
        │        │                                     │
        │        ▼                                     │
        │   发请求：历史 + 工具清单 ──────→ Provider     │
        │        ▲                          │          │
        │        │                429/超时/5xx → 重试   │
        │        │                          ▼          │
        │        │                模型回复 ModelTurn    │
        │        │                          │          │
        │        │                先记账：回复入历史 ◄──┤
        │        │                          │          │
        │        │              ┌─ 无工具调用 → 结束 ───┼──→ completed / refused / truncated
        │        │              ▼                        │
        │        │        循环守卫：相同动作 ≥3 次？──是──┼──→ stuck
        │        │              │ 否                     │
        │        │              ▼                        │
        │        │        执行工具，结果挂 tool_call_id   │
        │        │              │                        │
        │        └──────────────┴── 结果入历史，再发回模型 │
        │                                              │
        │   兜底：max_iterations 用完 → max_iterations   │
        └──────────────────────────────────────────────┘
```

核心认知：**模型本身无状态、不会循环。循环存在于 Harness 代码里，模型每轮只是"看一遍历史，给一次反应"。**

###顺序
1. 用户的话 → 存进历史
2. 历史发给模型
3. 模型回复（"直接回答" 或 "我要调工具X"）→ 先存进历史      ← 你漏的就是这半步
4. 如果是工具调用：代码执行工具 → 结果存进历史 → 回到第 2 步
5. 如果是直接回答：循环结束


## 三个为什么

- Q: 为什么工具结果必须用 tool_call_id 挂回对应调用，而不是按顺序追加？
  A: 并行调用 + **部分失败时顺序不可靠**——两个调用一成一败，结果必须明确挂回各自调用，模型才知道谁成谁败；真实 API 服务端会校验这条因果链，孤儿结果直接报错。

- Q: 为什么工具报错要包装成数据喂回模型，而不是崩溃或告知用户失败？
  A: (1) 崩溃丢掉整场对话历史，之前所有轮次工作全废；
  (2) 很多错误模型能自己修（缺参数就补上重试）——错误即数据，loop 才有自愈能力。证据：invalid_args 场景模型首次给空参数 `{}`，收到错误后自行修正成功。

- Q: 模型无限重复同一调用会怎样？怎么防？
  A: 后果是每轮空烧 token（成本失控）+ 用户面对无限循环。两道防线：循环守卫（"工具名+参数"指纹相同第 3 次判 stuck）+ max_iterations 上限兜底。

## 一句话总结（面试可直接说）

"Agent 的本质是 Harness 代码里的一个循环：模型每轮看完历史要么回答、要么声明工具调用；我的代码负责执行工具、用 tool_call_id 把结果挂回调用、塞回历史再问模型。工程上四个关键点：id 因果链、先记账后执行、工具失败即数据让模型自愈、循环守卫防死循环。"
