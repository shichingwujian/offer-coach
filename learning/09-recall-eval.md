# 09 | 召回评估集：先造尺子，再造轮子

> D11 学习笔记（explain-back #9 通过）。代码在 `src/offer_coach/evaluation/`，评估集在 `eval/recall_set.jsonl`，81 个测试全过。

## 一句话本质

改检索不能靠"感觉变好了"。先造一把尺子（54 条带标准答案的查询），每次改完量一遍，**数字涨了才算真的好**。

## 全景地图：检索发生在哪

诊断流程五步：给稿子 → analyze 打分暴露薄弱点 → **★ 模型自己填检索词调 query_knowledge_base ★** → 拿高手答对照 → 出报告。评估集就是把 ★ 这一步单独揪出来打分。

检索拉胯的后果：模型没了题库弹药，报告凭模型记忆写 → 幻觉风险（D6 做 RAG 的意义白搭）。

## 三个核心概念

- **recall@5**：前 5 个结果里命中标准答案的比例。@5 因为只塞 top-5 给模型——第 6 名等于不存在。检索按**相关度**排队（不是"对错"，它不懂对错）
- **三种查询类型**（尺子的刻度）：
  - keyword 关键词型 = 模型正常发挥提炼的好词
  - paraphrase 转述型 / scenario 场景型 = 最坏情况（用户原话直接进检索）
- **注入式评估器**：`run_recall` 只认"查询进、题目出"接口，检索函数可换——同一把尺子量 FTS5 和将来的混合召回（依赖注入第 6 次）

## 基线数字（2026-10-14，纯 FTS5）

**recall@5 = 37.0%（20/54）**：keyword 100% / paraphrase 0% / scenario 0%。

关键发现：34 条漏网全是"无结果"——不是查错，是压根没查到。元凶：**整句短语匹配**——查询必须一字不差、连续出现在题面里才认。像死板的图书管理员：报出书名原话秒找，自己描述内容就两手一摊。

面试注脚：生产中模型会提炼关键词再调工具，所以真实差距没 0% 那么惨——但那是靠模型自觉兜底，检索层自己经不起自然语言。
