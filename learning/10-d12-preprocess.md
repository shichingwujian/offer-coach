# 10 | 查询预处理：拆词三刀 + 检索名词扫盲

> D12 学习笔记（含问答记录：rowid / FTS5 / ORDER BY / 两个通道）。代码在 `src/offer_coach/knowledge/preprocess.py` 和 `db.py` 的 `search_smart`，92 个测试全过。

## 一句话本质

查询在进检索**之前**先拆成关键词（词与词是 OR 关系），检索引擎一行不改。recall@5 从 37.0% → 72.2%。

## 名词扫盲（用户问答记录）

- **rowid = 货架编号**：SQLite 每存一行自动盖的序号（1、2、3……807）。我们按分类目录字母序灌库，字母靠前的目录里的题 rowid 小。不写排序规则时，SQLite 默认按 rowid 返回 = 按"上架顺序"返回，和相关度无关
- **FTS5 = SQLite 自带的搜索引擎模块**（Full-Text Search 第 5 版）。普通数据库查"这一行等于什么"快，查"文字里包含什么词"慢；FTS5 是"按内容找文字"的加速器。建表写 `USING fts5` 即启用，它会建倒排索引（索引页：词 → 哪些行含它）
- **ORDER BY = SQL 的排队规则**。SQL 是跟数据库说话的语言：`WHERE` = 筛选条件（只要麻辣烫），`ORDER BY` = 排序方式（按评分/按距离），`LIMIT` = 只看前几家。不写 ORDER BY 就像外卖列表不选排序——按商家入驻顺序列
- **两个通道 = 代码里的一个 if-else 分流**（db.py:56-71）：≥3 字走 MATCH（翻索引页，有 ORDER BY rank 按相关度排）；<3 字走 LIKE（逐行扫描，无排序，按 rowid 先到先得）。类比银行取号：普通业务 A 窗口按叫号，特殊业务 B 窗口先到先得。必须分流是因为 trigram 索引页里根本不存在 2 字的词

## 拆词三刀（preprocess.py）

1. **标点切段**：按标点/空白切开
2. **停词当刀**：废话词清单（的/了/把/是/什么/面试官问我……）当分隔符切，长的先切（`sorted(STOPWORDS, key=len, reverse=True)`——否则"问"先把"面试官问我"切碎，碎肉拼不回整鱼）
3. **长段滑窗**：≤4 字或非纯中文（MCP、IVF_FLAT 是原子的）整留；纯中文长段整留 + 滑窗二字块。切错的噪音词查不到即无害（OR 合并：多切无害，漏切才有事）

## 合并排序（search_smart）

每词各查一遍（复用 search_questions 双通道），记账本合并：**标题命中 2 分 / 正文 1 分，同分比最佳名次，每词 limit×4 进合并池**，最后切 top-5。

## keyword 回退 bug 解剖（面试素材）

症状：v1 按命中词数排序，`工具 schema` 这条 keyword 从 100% 掉到 95%。
归因链：`工具`（2 字）走 LIKE 通道 → 无 ORDER BY 按 rowid 先到先得 → 目标题上架晚没进前 5 池 → 它明明两个词都中，却只能带 schema 池的 1 次命中孤军奋战 → 同分比名次被挤掉。
修复：池子 limit×4（让它进得来）+ 标题加权（让它排得前）。
**一句话（可背）**：MATCH 走索引按相关度排，LIKE 全表扫描按入库顺序排——两条通道排序语义不同，合并必须自己补排名逻辑。**拆词解决"查不到"，引入"排不准"**；召回和排序是两个独立问题。
