# 06 | Context 层：模型的桌面管理

> D7 学习笔记。代码在 `src/offer_coach/context/`，40 个测试全过。

## 一句话本质

模型是金鱼——两次调用之间什么都不记得，"记忆"是我们每轮重发的 history。Context 层就是管这叠历史的：**别让雪球滚爆桌面**。

## 核心概念（大白话版）

- **桌面** = 上下文窗口（DeepSeek 64K tokens），模型一次能"看"的东西的上限
- **桌面预算** = 我们主动定的上限（6000），不是钱，是"地方"。为什么不堆满？两宗罪：① 历史每轮重发，input 按量计费，雪球越滚越贵；② 注意力稀释——桌面越乱模型越找不到重点
- **死保区** = system 剧本 + 第一条 user（任务锚点），永远留——丢了剧本模型就忘了自己是谁
- **滑窗区** = 其余历史从后往前装，预算满就扔老的

## 孤儿与打包箱（本层灵魂）

模型每用一次工具，历史留两条痕迹：① assistant 订单（带 tool_calls，单号 c3）② tool 回执（挂 tool_call_id="c3"）。

裁剪时若扔了①留下②，回执就变成**孤儿**——API 规则是"每条 tool 消息必须能指到前面的订单"，指不到就报错拒绝。

`_blocks()` 的解法：**打包**——订单和它的回执捆成一个包裹，裁剪只能整包扔整包留。让坏事在结构上无法发生，比"裁完再检查"高级。

## 设计细节：两份历史

`run_loop` 里裁剪只作用于 `outbound`（发给金鱼的副本），内部 `history` 完整保留。给模型看的可以剪，自己的账本必须全。

## 为什么摘要压缩推迟 v2（D005）

三种武器里只有摘要"要花钱+会出错"（要多调一次模型总结历史，引出摘要预算/质量/递归摘要一串新问题）；当前 diagnose 仅 4-6 轮，离窗口远得很；滑窗是此刻就在保命的底线。面试话术："我知道下一步是什么，只是还没做"比"我全做了"更像工程师。

## 埋给 v2 的钩子

摘要作为 `fit` 的可替换策略接入：老历史 → 模型总结成一段话留档，主结构不动。
