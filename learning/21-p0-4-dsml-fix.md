# 21 | P0-4：DSML 泄漏修复——收尾轮放行零成本工具 + 终答哨兵

> 2026-10-21。真实长稿验收钓出的事故（见 [[20-long-acceptance]]），药方①+② 组合落地。
> 考试环节用户选择跳过（"直接修复吧"），三个为什么的答案直接记录在此。

## 事故一句话

预算耗尽 → 收尾轮工具菜单清空 → 模型想调 generate_report 没工具 →
把工具调用写成 DSML 标记文本当终答 → 终答非空判 full → 用户拿到乱码。

## 修复后的数据流

```text
预算耗尽
  → 收尾轮 1：菜单 = 白名单（diagnose 点名 generate_report）
      ├─ 模型调 generate_report → 正常执行（过 hooks，不计预算）→ 回执挂历史
      │    → 收尾轮 2：真·无工具（白名单置空）→ 模型看着排版结果写终答 → full
      ├─ 模型调白名单外工具 → 补 budget_exceeded 回执 → tool_budget_exceeded
      └─ 模型直接答 → completed
  → diagnose 终答哨兵：正文含 DSML/<invoke 等标记 → 不判 full，改判 degraded
```

两层关系：白名单治**根因**（别把传真机收走），哨兵是**烟雾报警器**
（万一还漏——换模型、新泄漏形态——交付物永远不是乱码冒充完整报告）。

## 三个为什么（答案记录）

**Q1：为什么白名单由 diagnose 层传，而不是 loop 自己判断"哪个工具零成本"？**
loop 是通用引擎，只认识"工具菜单"和"预算计数"；"哪个工具免费"是业务知识
（generate_report 恰好是纯模板）。让 loop 猜成本 = 引擎层渗进业务判断，
以后换一批工具 loop 就得改。白名单是参数，业务层点名，引擎层照做——分层不动。

**Q2：白名单工具执行完后，为什么还要再补一轮真·无工具收尾，
而不是直接把工具结果当终答返回？**
loop 的出口合同是"终答来自模型"，全程没有例外；为这个特例开洞，
合同就变成"有时终答来自工具"，下游（diagnose 判 full、记忆写摘要）
都要多处理一种来源。补一轮的代价是一次纯文本调用（便宜），
换来的是合同干净。而且模型看着排版好的回执写终答，通常会原样复述交付。

**Q3：哨兵为什么放在 diagnose 层，而不是下沉到 loop 层改 LoopStatus？**
DSML 标记在协议层是**合法终答**——模型没下单，stop_reason 正常，loop
没被骗，它如实报告了"模型给了一段文本"。"这段文本算不算有效交付物"
是业务判定（诊断报告不该含工具标记，但别的业务也许合法）。
loop 管协议诚实，diagnose 管业务口径——各管各的。

## 顺带的旋钮

- CLI 新增 `--max-tool-calls` / `--max-kb-calls`（diagnose_run 的参数早就留着，CLI 没接）
- kb 预算默认值 3 → 5：真实验收中 4000 字长稿模型想查 8 次，3 次确实偏紧。
  预算是旋钮不是 bug 修复——调旋钮降触发频率，白名单+哨兵管触发后不出事。

## 边界

- 哨兵清单刻意短（DSML / <invoke / tool_calls_begin / <function_calls）：
  正经报告不可能含这些字样，宁可少匹配也不误伤
- 白名单执行照样过 pre/post 插件：权限闸在收尾轮不放假
- 白名单不计预算：预算防的是烧钱工具，零成本工具不在防范对象内
- 收尾轮白名单执行最多一轮（执行完白名单置空递归），不会变成新的循环通道
